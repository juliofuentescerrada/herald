## ADDED Requirements

### Requirement: H3 has a traceable functional definition

The maintained documentation SHALL define H3 actors, authority, boundaries, competition and result rules, exceptions, journeys, target acceptance and implementation gates in the English Markdown format of the H2 extension. It SHALL retain the baseline's single decision register and distinguish existing direction, proposed defaults and implemented behaviour.

#### Scenario: A reader finds the H3 definition

- **WHEN** a reader follows the H3 link from the README, roadmap or functional baseline
- **THEN** the extension explains elimination, single match, individual/direct-team invariants, seeding/byes, progression, profiles, corrections and protected web/API journeys
- **AND** its proposed defaults resolve to D-39–47 without claiming approval or production implementation

#### Scenario: A reader assesses elimination exceptions

- **WHEN** a reader reviews the six-entry example, a double departure or a correction after dependent publication
- **THEN** the documentation distinguishes played wins, initial byes, administrative advances and sources without a qualifier
- **AND** it exposes exceptional placing/closure and publication/correction gates rather than inventing a winner or inheriting a league points rule as advancement

#### Scenario: A reader prepares a production slice

- **WHEN** a reader uses the discovery to propose H3 implementation
- **THEN** inherited and H3 policy/design/visual gates remain explicit, optional direct score and ordered detail remain conditional, and product acceptance is not presented as executed tests
- **AND** implemented specifications, runtime event inventory and H1/H2 implementation history remain unchanged by this documentation change
